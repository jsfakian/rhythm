# RHYTHM Manifest Generator — Instructions for Partners

Tool for RHYTHM partner institutions to prepare the Excel metadata, anonymized CT ZIP files, and JSON manifest needed for the [v2 Server-Assigned Batch upload](../README.md#v2-server-assigned-batch-recommended).

> **Important:** this tool does **not** anonymize DICOM files. All CT studysets must already be anonymized locally, before packaging, by the submitting institution. The tool only reads already-anonymized ZIPs and builds the upload manifest — the final RHYTHM Repository Study ID is always assigned by the server, never by this tool.

## Files in this folder

| File | Purpose |
|---|---|
| `create_rhythm_server_assigned_manifest_gui_with_uid.py` | The tool — cross-platform Python script (GUI or CLI) |
| `RHYTHM_manifest_tool.exe` | The same tool, packaged as a Windows executable — no Python install required |
| `rhythm_server_assigned_metadata_template.xlsx` | Excel template partners fill in, one row per studyset ZIP |
| `rhythm_upload_manifest.json` | Example of the manifest the tool generates |
| `rhythm_automated_upload_instructions_for_tool.html` | Standalone HTML version of these instructions (self-contained, can be opened offline or emailed to a partner) |

## 1. Purpose

Each partner prepares:

1. An Excel metadata file with one row per CT studyset.
2. One ZIP file per anonymized CT studyset.
3. A JSON manifest generated by this tool.

The JSON manifest is uploaded together with the ZIP files through the RHYTHM Repository Upload Platform. The server validates the upload and assigns the final Repository Study ID — the partner never assigns it manually.

## 2. Privacy and anonymization requirements

Before using this tool, all CT studysets must already be anonymized locally by the submitting institution.

The ZIP files and Excel template must **not** contain:

- Patient name
- Original hospital `PatientID`
- Accession number
- Date of birth
- National identifier
- Any other direct patient identifier

The tool does **not** anonymize DICOM files. It only prepares the upload manifest, and it actively rejects a metadata template that contains obviously-identifying columns (`patient_name`, `birth_date`, `national_id`, etc. — see `FORBIDDEN_COLUMNS` in the script).

## 3. Recommended folder structure

Create one working folder, for example:

```
RHYTHM_Upload/
├── metadata/
│   └── rhythm_server_assigned_metadata_template.xlsx
├── zips/
│   ├── study_001_anonymized.zip
│   ├── study_002_anonymized.zip
│   └── study_003_anonymized.zip
└── output/
```

The `zips` folder should contain the anonymized CT studyset ZIP files. Each ZIP should contain **one CT studyset only**.

## 4. Completing the Excel metadata template

Open `rhythm_server_assigned_metadata_template.xlsx` and complete one row per ZIP file:

| Column | Description |
|---|---|
| `filename` | Exact ZIP filename, e.g. `study_001_anonymized.zip` — must match a file in the selected ZIP folder |
| `site_code` | Coded submitting site, e.g. `S001` |
| `clinical_indication_code` | See table below |
| `anatomical_region` | e.g. `Head`, `Chest/HRCT`, `Abdomen` |
| `contrast_code` | `NC`, `CE`, or `MIX` |
| `patient_group_code` | See table below |
| `scanner_id` | Locally registered CT scanner ID, e.g. `CT01` |
| `protocol_name` | Name of the CT protocol used |
| `patient_weight_kg` | Patient weight in kg |
| `patient_age_years` | Patient age in years |
| `ctdivol_mgy` | CTDIvol in mGy |
| `dlp_mgy_cm` | DLP in mGy·cm |
| `image_quality` | Image-quality category, e.g. `Acceptable` |

**Clinical indication codes**

| Code | Meaning |
|---|---|
| `HEADTRAUMA` | Head / Trauma |
| `MASTOID` | Mastoid bone / Inner ear |
| `CHESTCOMP` | Chest / Complicated infections |
| `CHESTFUNG` | Chest / Fungal infections |
| `HRCTILD` | Chest/HRCT — interstitial lung disease and related conditions |
| `ACUTEABD` | Abdomen / Acute abdomen |
| `LYMPHOMA` | Neck-Chest-Abdomen / Lymphoma |
| `CHESTABD` | Chest-Abdomen / Tumor staging and follow-up |

**Contrast codes**

| Code | Meaning |
|---|---|
| `NC` | Non-contrast |
| `CE` | Contrast-enhanced |
| `MIX` | Non-contrast and contrast-enhanced / mixed |

**Patient group codes**

| Code | Meaning | | Code | Meaning |
|---|---|---|---|---|
| `PH-G1`–`PH-G4` | Pediatric Head, Groups 1–4 | | `PB-G1`–`PB-G5` | Pediatric Body, Groups 1–5 |
| `YA-G6` | Young Adult | | | |

> ⚠️ These coded fields are free-text strings in the manifest schema — the server does not reject an unrecognized code at upload time, so use the values above exactly as shown.

## 5. Preparing ZIP files

- One ZIP file corresponds to one CT studyset.
- The ZIP should contain DICOM files only, where possible — no identifiable reports, screenshots, or hospital exports.
- The ZIP filename must exactly match the `filename` column in the Excel template.
- The ZIP must not contain multiple different `StudyInstanceUID` values.

The tool inspects each ZIP file and extracts the anonymized DICOM `StudyInstanceUID`.

## 6. Running the tool

### Windows executable

Use `RHYTHM_manifest_tool.exe` if you don't have Python installed:

1. Double-click the executable.
2. Select the completed Excel metadata template.
3. Select the folder containing the ZIP files.
4. Select where to save the output JSON manifest.
5. Optionally enter a batch ID, e.g. `S001-2026-07-12-001`.
6. Keep **Include ZIP SHA-256 checksums in manifest** enabled.
7. Click **Generate JSON Manifest**.
8. Wait until the tool reports that the manifest has been created successfully.

### Python script

```bash
pip install pydicom openpyxl

# Graphical interface
python create_rhythm_server_assigned_manifest_gui_with_uid.py

# Or command-line use
python create_rhythm_server_assigned_manifest_gui_with_uid.py \
  --input metadata/rhythm_server_assigned_metadata_template.xlsx \
  --zip-folder zips/ \
  --out output/rhythm_upload_manifest.json \
  --batch S001-2026-07-12-001
```

(On Windows `cmd.exe`, use `^` instead of `\` for line continuation.)

Either way, the tool produces:

- `rhythm_upload_manifest.json` — submit this together with the ZIP files
- `rhythm_upload_manifest_index.csv` — for your own review, not submitted

## 7. What the tool checks

Before writing the output, the tool verifies:

1. The metadata file can be read.
2. The required metadata columns are present (and no forbidden/identifying columns are present).
3. Each `filename` exists in the selected ZIP folder.
4. Each listed file is a valid ZIP archive.
5. Each ZIP contains readable DICOM files.
6. Each ZIP contains exactly **one** DICOM `StudyInstanceUID` (and, under it, one `PatientID`).
7. The DICOM `StudyInstanceUID` can be extracted and included in the JSON manifest.
8. A ZIP SHA-256 checksum can be calculated, if enabled.

If a ZIP contains more than one `StudyInstanceUID`, the tool stops with an error — split the ZIP so each contains only one CT studyset, and re-run.

## 8. What the generated JSON contains

Example item from `rhythm_upload_manifest.json`:

```json
{
  "ref": "ROW0001",
  "filename": "study_001_anonymized.zip",
  "dicom_uid": "2.25.23890534782093478203948203948203948",
  "dicom": {
    "patient_id": "P-8F3KQ9M2X7AD",
    "series_uids": ["2.25.90823475098237450982374509823745098"],
    "series_count": 1,
    "instance_count": 180
  },
  "site_code": "S001",
  "clinical_indication_code": "HEADTRAUMA",
  "contrast_code": "NC",
  "patient_group_code": "PH-G4",
  "image_quality": "Acceptable"
}
```

`dicom_uid`/`dicom` are informational only — the server independently re-extracts the `StudyInstanceUID` from the ZIP rather than trusting these fields.

## 9. Uploading to the repository

Upload `rhythm_upload_manifest.json` together with all the ZIP files it lists, through the **Automated Upload** page (`/automated-upload/`, requires a logged-in account) on the RHYTHM Repository Upload Platform. The server will:

1. Verify each ZIP's SHA-256 checksum, if the manifest supplied one.
2. Re-validate GDPR anonymization against `GDPR-strict.json`.
3. Independently extract the DICOM `StudyInstanceUID` from the ZIP (it does not trust the manifest's `dicom_uid` field).
4. Check for duplicate studies.
5. Assign the final Repository Study ID: `RHY-{SITE}-{INDICATION}-{CONTRAST}-{GROUP}-{SEQNO}`, e.g. `RHY-S001-HEADTRAUMA-NC-PH-G4-000123`.
6. Push validated images to Orthanc.

Assignment happens **asynchronously** — track progress on the **My Uploads** page (`/my-uploads/`) or by polling the job status URL returned when the upload completes.

## 10. Troubleshooting

| Problem | Fix |
|---|---|
| ZIP file not found | The Excel `filename` must exactly match a file in the selected ZIP folder |
| File is not a valid ZIP | Re-create it with standard ZIP compression |
| No readable DICOM files found | Check the ZIP holds DICOM files, not a nested ZIP or only screenshots/reports |
| Multiple `StudyInstanceUID` values found | The ZIP has more than one study — split it, one ZIP per studyset |
| Multiple `PatientID` values found | May indicate mixed datasets or inconsistent anonymization — review the ZIP contents |
| Excel file cannot be read | Python: `pip install openpyxl`. Executable: close the Excel file before running the tool |
| DICOM UID extraction fails | Python: `pip install pydicom`. Also confirm the ZIP contains valid DICOM files |

## 11. Final checklist before upload

- [ ] All CT studysets are anonymized
- [ ] Each ZIP contains one CT studyset only
- [ ] No ZIP contains direct patient identifiers
- [ ] The Excel template has one row per ZIP, and each `filename` matches a ZIP exactly
- [ ] The manifest generated successfully with no reported errors
- [ ] The ZIP files and the JSON manifest are uploaded together
- [ ] The Repository Study ID was **not** assigned manually — the server assigns it
